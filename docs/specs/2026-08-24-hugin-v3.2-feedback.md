## Post-implementation corrections (2026-08-25)

Eight findings from final review, against the built implementation rather than this spec:

1. **Sources seeding is initializer-once, not "when-empty."** Item 6 says the db seeds "a Sources table" from defaults; the actual gate is a marker row (`SyncState` with `Source = "sources-seed"`) written once in `HuginDbInitializer.InitAsync`, not a check for an empty `Sources` table. This matters: deleting every source by hand does **not** resurrect FINN/LinkedIn/Proff on the next launch — the marker row already exists, so the seed step is skipped. An empty-table check would have restored them, which is the wrong behavior for a user who removed defaults on purpose.
2. **Proff's seeded URL is the generic front page.** `https://www.proff.no`, per item 6's "GENERIC job-search front pages" instruction — no fylke/kommune/category baked in, matching FINN's `https://www.finn.no/job` and LinkedIn's `https://www.linkedin.com/jobs/`.
3. **Settings-owns-sources refresh contract.** Rather than the dashboard's `SourcesCard` polling or the two views sharing state directly, `App.tsx` holds a `sourcesVersion` counter (bumped by `SettingsView`'s `onSourcesChanged` callback after any add/edit/remove/reorder) and forwards it to `DashboardView` as a `refreshToken` prop; `SourcesCard` refetches whenever that token changes. Keeps Settings and the dashboard decoupled — neither imports the other's state.
4. **Company-detail tabs reused the design system's existing component instead of the plan's sketch.** Item 5's plan called for new tab CSS; the design system already ships `.tab-list`/`.tab` (accent-underline styling), so `CompanyDetail.tsx` wires the hovedenhet + branch tabs to that instead of adding project-local tab styles.
5. **Leftover 9j's brief example didn't match the actual failure mode.** The brief's motivating example (a malformed kommune number causing `n[..2]` to throw) doesn't reproduce — a 2-character slice on a string of length ≥ 2 never throws in C#. What actually needed fixing was semantic: a non-4-digit value (too short, too long, non-digit) reached Brreg as a silently wrong query. Implemented as an explicit 4-digit validation (`IsValidKommuneNumber` in `SyncService.SyncBrregAsync`) applied ahead of both the plain-municipalities path and the fylke-expanded/chunked path, surfacing a clear Norwegian error instead.
6. **Leftover 9f pinned the existing behavior: first-write-wins on employer homepage within a sync run.** `AdoptWebsiteAsync` only fills a company's website when it's currently null (or a confirmed-dead check) — so when two ads in the same run carry different `employer.homepage` values for the same employer, the first one processed claims the slot and the second is dropped. `SyncServiceTests.Two_ads_for_the_same_employer_with_different_homepages_pin_the_first_one_adopted` documents this as a pin of pre-existing upsert behavior, not a new rule.
7. **Leftover 9k probe result: `allOfNorway` is safe today, with thin headroom on the widest chunk.** Live-probed 2026-08-25 with the sync's real query shape (`naeringskode=62&kommunenummer=0301&size=200`): Oslo — the widest realistic per-fylke chunk — holds 9,671 enheter (49 pages) and 7,071 underenheter, inside Brreg's 10,000-item deep-pagination window. Requesting past the window (page 50 at size 200) returns HTTP 400, which would fail the Brreg sync source loudly with a visible error — never a silent truncation. Recommendation: nothing to change now; if Oslo NACE 62 approaches 10,000 enheter (~3% growth), sub-chunk that fylke by NACE sub-code (62.01/62.02/62.03/62.09) before advertising all-of-Norway further.
8. **Nav-click always returns to the companies list, not an open detail.** Item 4 said back/forward should land "while keeping the v3.1 in-session state persistence." Filters, search, scroll, and keep-mounted views all still persist — but clicking the Companies nav entry now navigates to the list URL, so an open company detail is left via the browser's Back button rather than being re-shown on nav-click (in v3.1 the drill-in was view-local state and survived switching views). Conventional SPA routing; Back does return to the detail, which v3.1 could not do.
