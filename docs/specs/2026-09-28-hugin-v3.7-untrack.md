# Hugin v3.7 — `untrack` and a duplicate warning in `track`

2026-09-28. A morning run tracked a branch office as *applied*, although the same application
already sat in the pipeline as *applied* under a sister company with its own orgnr. Two rows
for one application, and no way to remove either: the CLI has no delete, and neither has the
API or the dashboard. The only code that deletes pipeline rows is the full reset
(`ResetService`), which wipes all of them.

This wave adds two things, released together:

1. **`hugin untrack <orgnr>`** removes one pipeline row.
2. **`hugin track` warns** when a company it is about to add for the first time looks related
   to one already tracked: same family in the register, or the same brand name.

The first repairs the mistake; the second makes it harder to repeat.

Examples in this spec and in the tests use invented companies (AKME …) and test orgnr. The
real case is recorded in my private notes, not in this repo.

## Decisions locked (2026-09-28)

1. **The warning matches family *and* brand.** The register alone would not have caught the
   case that triggered this wave: the branch belonged to a parent in Oslo, while the company
   already tracked was a separate company with no parent. What they shared was the first word
   of the name (and a street address Hugin does not store). Family-only matching was rejected
   because it misses exactly that case; address matching was rejected because it needs a new
   column, a migration and a Brreg backfill for the same result.
2. **Warn, never block.** The row is still written; the warning says what matched and how to
   undo it. A false alarm costs one line of output, a refusal would break the scripted morning
   run.
3. **Warn only on a new row.** Re-tracking an orgnr that is already in the pipeline (moving its
   status, adding a note) never warns — the relationship was already accepted once.
4. **No confirmation prompt on `untrack`.** The CLI is run non-interactively (`/morning`).
   Instead it prints the full row it removed, which is the only record left afterwards.
5. **CLI only in this release.** No API endpoint, no dashboard button, and the API's track
   response does not carry the new warning. The repository method is written so any of those
   can reuse it later.
6. **Companies are never deleted.** `untrack` removes the pipeline row only; the company row
   stays, as the `Company` model already promises.

## Part A — `untrack`

### A1. Command

```
hugin untrack <orgnr>
```

- `CommandParser` gets an `"untrack"` verb → `UntrackCommand(string Orgnr)`.
- Missing orgnr → `InvalidCommand("mangler orgnr — bruk: hugin untrack <orgnr>")`.
- Any further argument → the existing `ReadOptions` error (`uventet argument '…'` /
  `ukjent valg '--…'`). No options are accepted.
- The orgnr is not format-checked, the same as `track`: an unknown value simply is not
  tracked (A4).
- The unknown-verb message lists `untrack` among the commands.

### A2. Repository

`IPipelineRepository` gains:

```csharp
/// <summary>Removes the entry for <paramref name="orgnr"/> and clears every manual ad link
/// (<see cref="Ad.LinkedOrgnr"/>) pointing at it, in one save. Returns the removed entry and
/// how many links were cleared; null when the orgnr is not tracked.</summary>
public Task<PipelineRemoval?> DeleteAsync(string orgnr, CancellationToken ct = default);
```

```csharp
public sealed record PipelineRemoval(PipelineEntry Entry, int LinksCleared);
```

- `EfPipelineRepository`: load the entry; if absent return null. Otherwise
  `db.Pipeline.Remove(entry)`, set `LinkedOrgnr = null` on every `Ad` whose
  `LinkedOrgnr == orgnr`, then **one** `SaveChangesAsync` so the two changes land together.
- Why clear the links: `PUT /api/ads/{feedId}/link` refuses an untracked target, so a link must
  never outlive its entry. Reads already ignore a dangling link (`AdOverviewService.MatchAsync`
  falls through), so this is hygiene, not a crash fix — but the dashboard's «Koble fra» state
  would otherwise show a link to nothing.
- Ads whose `EmployerOrgnr` equals the orgnr are untouched; that is the feed's own data.
- The test fake (`Fakes.cs`) implements the same contract.

### A3. Service

`PipelineService.UntrackAsync(string orgnr, CancellationToken ct)` →
`UntrackResult?` = `(PipelineRemoval Removal, string? CompanyName)`. Null when not tracked.
The company name is read from `ICompanyRepository` for the printout; a missing company row
gives a null name, not an error.

### A4. Output

Success, exit 0:

```
Fjernet 111111111 AKME PROFESSIONALS AS AVD HEDMARK fra oppfølgingen.
  Status: søkt
  Stjernemerket: ja
  Grunn: …
  Notat: …
  Svar: …
  Opprettet: 2026-09-28
  Sist endret: 2026-09-28
  1 annonselenke fjernet.
```

- Status uses the existing `StatusLabel`. `Stjernemerket` only when starred; Grunn/Notat/Svar
  only when non-empty, the same rule as `track`'s printout. Dates are `Created` and `Updated`
  as local dates, `yyyy-MM-dd`. The link line only when `LinksCleared > 0`.
- No company name → the orgnr alone on the first line.
- Not tracked → stderr `Feil: 111111111 følges ikke opp.`, exit 1, nothing changed.
- `untrack` never touches the network.

### A5. Help and README

- `PrintUsage` gets `hugin untrack <orgnr>          Fjern en bedrift fra oppfølgingen` under
  `track`.
- README CLI table gets a `hugin untrack <orgnr>` row: removes one pipeline row, clears manual
  ad links to it, keeps the company, cannot be undone.

## Part B — the warning in `track`

### B1. Registry root, shared

`AdOverviewService.ResolveRootAsync` (follows `ParentOrgnr` upward, max 4 hops, stops at a
missing row, a missing parent or a self-reference; a missing row means the orgnr is its own
root) moves unchanged to a small static helper in `Hugin.Core/Services/RegistryRoot.cs`:

```csharp
public static class RegistryRoot
{
    public const int MaxHops = 4;
    public static Task<string> ResolveAsync(ICompanyRepository companies, string orgnr, CancellationToken ct = default);
}
```

`AdOverviewService` calls it; its existing tests prove the move changed nothing.

`ParentOrgnr` is Brreg's `overordnetEnhet`: a branch's hovedenhet, or a public body's parent.
It is **not** group (konsern) membership, which the register API does not expose.

### B2. Brand token

`Hugin.Core/Services/BrandName.cs`:

```csharp
public static class BrandName
{
    /// <summary>The first distinctive word of a company name, lower-cased; null when the name
    /// has none.</summary>
    public static string? Token(string name);
}
```

- Split on every character that is not a letter or digit (`char.IsLetterOrDigit`, so æøå
  survive). Lower-case with the invariant culture.
- Skip a word when it is shorter than 3 characters, all digits, or in the stop list. Return the
  first word left; null when none is left.
- Stop list (one `HashSet`, ordinal): legal forms and branch markers `as asa ans nuf enk avd
  avdeling`; generic words `norsk norske norge norway nordic the and for`, `it data digital
  tech teknologi technology systems system solutions services service consulting konsulent
  group gruppen holding partner partners`. (Words under 3 characters are already skipped by
  the length rule and are not listed.)
- Examples the tests pin: `AKME PROFESSIONALS AS AVD HEDMARK` → `akme`;
  `AKME IT SOLUTIONS AS` → `akme`; `FJELLTOPP DATA AS` → `fjelltopp`; `1-2-3 AS` → null;
  `NORSK SKOGSDRIFT AS` → `skogsdrift`; `IT DATA AS` → null; `ØSTLANDSK DIGITAL AS` →
  `østlandsk`.
- The list is a judgement call and will be wrong sometimes. That is acceptable only because the
  result is a warning (decision 2).

### B3. Finding relatives

Inside `PipelineService.TrackAsync`, **after** the company is known (fetched from Brreg if
needed) and **only when** `existing is null`:

1. `newRoot = RegistryRoot.ResolveAsync(companies, orgnr)`;
   `newToken = BrandName.Token(company.Name)`.
2. For each entry in `pipeline.GetAllAsync()` (every status): skip its own orgnr; load its
   company (skip the entry when the row is missing); it is a relative when
   - **family**: `RegistryRoot.ResolveAsync(entry.Orgnr) == newRoot`, or
   - **brand**: `newToken` is not null and `BrandName.Token(entryCompany.Name) == newToken`.
3. Collect `RelatedEntry(PipelineEntry Entry, string Name, RelationKind Kind)` where
   `RelationKind` is `Family` or `Brand` (family wins when both hold). Order by `Entry.Updated`
   descending, the same order `list` shows; ties by orgnr ascending.

Cost: one pass over the pipeline (tens of rows) with up to 4 company lookups each, once per new
track. No caching.

`TrackResult` gains `IReadOnlyList<RelatedEntry> Related` (empty list, never null). The API
endpoint ignores it (decision 5).

### B4. Output

After the normal `track` printout, on stderr, one line per relative, then one undo line:

```
⚠ ligner på noe du allerede følger opp:
  222222222 AKME IT SOLUTIONS AS (søkt) — samme merkenavn «akme»
  Angre: hugin untrack 111111111
```

- Family wording: `— samme hovedenhet i Enhetsregisteret` (never «konsern», see B1).
- The existing «mangler begrunnelse» warning is printed as before; the order is related first,
  then begrunnelse.
- Exit code stays 0: the write succeeded.

## Part C — testing (tests first, per task)

- **Parser:** `untrack 111111111` → `UntrackCommand`; missing orgnr; extra positional; unknown
  option; unknown verb message mentions `untrack`.
- **Repository (EF, in-memory SQLite like `RepositoryTests`):** delete removes the row and
  returns it; clears `LinkedOrgnr` on linked ads and reports the count; leaves ads linked to
  another orgnr alone; unknown orgnr → null and nothing changes.
- **`BrandName`:** every example in B2, plus an all-stop-word name.
- **`RegistryRoot`:** the existing `AdOverviewService` root tests stay green after the move.
- **`PipelineService` with fakes:**
  - `UntrackAsync` returns removal + name; null for an untracked orgnr; missing company → null
    name.
  - Warning: branch ↔ parent (family); two branches of one parent whose own row is missing
    (family); **the triggering shape** — a new branch whose parent is not tracked, and a
    tracked standalone company sharing its brand word (brand); unrelated companies (none);
    generic-only names (none); re-tracking an existing orgnr (none, even with a relative
    present); family + brand on the same entry (one line, `Family`); two relatives with equal
    `Updated` (orgnr order).
- **Build:** 0 warnings; C# and web suites green; Biome and `tsc` untouched but run.

## Part D — release

- Version **v3.7.0** (new command; last tag v3.6.2).
- The usual release path from my Hugin notes: PR, merge, tag, release with both Windows zips
  (Copy-Item staging), rebuild `publish\` and `publish-single\`, smoke-test the single exe from
  the zip. No demo redeploy needed — the demo has no CLI and the API is unchanged.
- **After release, on my real database:** `publish\hugin.exe list` first, `untrack` the
  duplicate row named in my private notes, then `list` again to confirm the original row is

- **Check that the morning run shows stderr.** The warning is useless if the scripted `track`
  step swallows stderr. That routine lives outside this repo; if it needs a change, that is a
  separate, approved edit.

## Out of scope, and known seams

- No API `DELETE /api/pipeline/{orgnr}` and no dashboard button (decision 5).
- The dashboard's track flow (Applications, «Følg opp» on an ad) does not show the relatives
  warning, although the service now computes it on those calls too.
- `untrack` has no undo. Re-tracking by hand from the printout restores status, grunn, notat
  and svar, but not `Created`, and the star only from the dashboard (the CLI has no star
  option).
- A brand match across genuinely unrelated companies that share a first word produces a false
  warning. Accepted.
- Companies of the same group that share neither a register parent nor a first word are not
  caught.

## Stress-test record (2026-09-28)

Four lenses run on the first draft; every finding folded in above.

1. 🟠 **Privacy — the draft disclosed my job applications.** It named the employers, the
   orgnr, the status and the date, and Part C put the real pair into public test code. Fixed:
   invented names and test orgnr throughout; the real case lives in private notes; the draft
   commit was amended before it was ever pushed.
2. 🟠 **Loophole — a mistaken `untrack` loses data silently.** The draft printout left out the
   star and the last-changed date, and did not say what re-tracking cannot restore. Fixed: A4
   prints both; the seams list names `Created` and the star.
3. 🟡 **Loophole — «konsern» was the wrong word.** `ParentOrgnr` is `overordnetEnhet`, not
   group membership. Fixed in B1 and B4.
4. 🟡 **Loophole — tie order unspecified.** Fixed in B3 (orgnr ascending) with a test.
5. 🟡 **Loophole — the warning may never be seen.** It goes to stderr with exit 0; a morning
   routine that hides stderr defeats it. Fixed: check added to Part D.

Security ✅ — the only new input is an orgnr passed to a parameterised EF query; `untrack` makes
no network call; output is plain console text. Accessibility ✅ — CLI text only; the warning is
words behind a glyph, never colour alone.

Considered and rejected:

- **Dangling link from a race.** A dashboard link PUT that runs between the CLI's delete and
  its save could leave a link to an untracked orgnr. Reads already ignore dangling links; one
  local user makes the window close to zero.
- **Skipping the relatives scan on API calls.** The scan runs on dashboard tracks and is thrown
  away. Tens of rows once per new track; a flag to skip it is more code than the cost.
- **Terminal escape sequences in register names.** Names come from Brreg's own register and are
  already printed by `list`; no new exposure.
- **A `--dry-run` or confirmation on `untrack`.** Scope growth against decision 4; the printout
  covers recovery.

## Post-implementation corrections (2026-09-28)

1. The stop list does not carry `as` or `it` (B2). The draft listed both and then said words
   under 3 characters are not listed; the length rule already skips them, so the code follows
   the second sentence.
2. The stop list gained `den det statens stiftelsen` (B2). Public bodies and foundations
   («Statens …», «Stiftelsen …», «Den norske …») would otherwise share a brand word and warn
   about each other on every new track. A real brand that starts with one of these words loses
   its brand match; a register parent still catches it as family.
3. `RegistryRoot` has four tests of its own (missing row, branch with a missing parent row,
   self-reference, the `MaxHops` stop) on top of Part C's "existing `AdOverviewService` root
   tests stay green".
4. The link line counts in the plural: `1 annonselenke fjernet.` but `2 annonselenker fjernet.`
   (A4 showed only the singular).
5. The test fake's ad store is exercised by one service-level `UntrackAsync` test that asserts
   `LinksCleared`, so the fake's link clearing is not dead test code. The EF repository tests
   remain the proof that the real links are cleared.
6. `TrackAsync` reads the company once and keeps its name for the relatives scan, instead of
   reading it again after a Brreg fetch (B3 "after the company is known"). No behaviour change.
