# Hugin v3.5 — "reach": wider bransje net, no assumed geography

2026-09-09. This wave replaces the v3.5 arc the v3.4 spec advertised. That arc — "adaptable:
NACE/keywords/categories as an editable focus profile" so Hugin could cover any field — is
**dropped**. Hugin stays a job radar for the Norwegian developer market, for me and for other
developers here. Covering nursing, teaching or trades was a large build for a benefit I do not
want, and other projects compete for the time.

What is left after dropping it is not nothing. Two real defects surfaced while re-reading the
code with developer-only as the goal:

1. **Company discovery is `naeringskoder: ["62"]` and nothing else.** Norsk Tipping AS
   (925836613, NACE 92.000, Hamar) is one of the largest developer employers in my region and
   can never enter Bedrifter. Neither can Sparebanken Innlandet, a telecom operator or a
   research institute. Ads from them still arrive — `AdFilter` gates on kommune, keyword and
   category, not on the employer's NACE, and `SyncService.EnrichEmployerAsync` fetches the
   employer row on demand — but *proactive* discovery, the list of employers worth an open
   application before they advertise, is blind to them.
2. **Hugin assumes it lives in Innlandet.** `HuginConfig` hardcodes Gjøvik, Hamar, Lillehammer
   and Ringsaker as defaults, `hugin.json.example` ships the same four, and `BootSyncGate`'s own
   summary records what Esc on the first-run dialog does: "releases it AND starts the sync with
   the config defaults". A developer in Tromsø who dismisses the dialog silently syncs my
   hometown.

The line the design follows: **geography is personal, bransje is domain knowledge.** Which
kommuner matter is only knowable by asking. Which industries employ developers in Norway is the
same answer in Tromsø as in Hamar — that Hugin can ship.

## Decisions locked (2026-09-09)

- Hugin remains developer-only. `categories` stays hand-edited: the NAV level-1 "IT" gate is
  what keeps it developer-only, and putting it in the UI is the door back to the dropped goal.
- `naeringskoder` and `keywords` become editable from Settings. `navToken` and `linkouts` stay
  hand-edited (sources already moved to the db in v3.2).
- The curated bransje set ships as a **default**, and reaches existing installs as a one-click
  "Legg til anbefalte" — never silently on upgrade, because a config file always beats a default.
- Kommune defaults become **empty**. Not-yet-chosen scope is a first-class state, distinct from
  broken scope.
- A **reset** is part of this wave, in two levels: clear the scope, or start over completely.
- Release: **v3.5.0**, both zips per the release rule. The TypeScript 7 upgrade (PR #15) rides
  along, as decided 2026-09-09.

## Part A — no assumed geography

1. **Empty defaults.** `HuginConfig.Municipalities` defaults to `[]`; `Fylker` and `AllOfNorway`
   already default to empty/false. `hugin.json.example` ships `"municipalities": []` with a
   comment that the first-run dialog fills it.
2. **"Scope not chosen" is its own state.** `SyncBrregAsync` today refuses an empty allow-set
   with "Kommuneregisteret er tomt — dekningen kunne ikke utvides", which is now the wrong
   message for the common case. Split it: no configured kommuner, fylker or `allOfNorway` →
   `SourceResult(false, 0, "Ingen dekning valgt — velg kommuner i dashbordet")`. The existing
   register-empty message stays for the case it was written for (scope configured, register not
   yet fetched).
   - **The CLI needs the actionable version of it.** `hugin.exe sync` has no first-run dialog, so
     a CLI-first user would otherwise be dead-ended by a message with no remedy. The CLI prints
     the config path, the key it needs (`municipalities`), and one line pointing at
     `hugin-api.exe` as the easy way to choose.
3. **`scopeConfigured` on `StatusDto`.** The first-run dialog currently opens on a client-side
   condition alone (`focus === null` in localStorage, `App.tsx:37`), which cannot see that the
   server has no scope. Add `bool ScopeConfigured` to `StatusDto` (true when municipalities,
   fylker or allOfNorway is non-empty) and open the dialog when `focus === null ||
   !scopeConfigured`. This is also what makes the reset in Part D visible to a browser that
   already has a stored focus.
4. **Esc no longer syncs my hometown.** `POST /api/first-run-dismissed` keeps releasing the gate,
   but with empty defaults there is nothing to fetch, so the held sync now ends as the honest
   "Ingen dekning valgt" from A2 rather than an Innlandet fetch. The dashboard renders that as a
   *velg dekning* prompt with a real `<button>` that reopens the dialog — an empty result, not an
   error — and announces the prompt through the existing live region, since it replaces the
   previous message asynchronously.
5. **Test fallout.** Eight places construct `new HuginConfig()` and lean on the Innlandet
   defaults; they get explicit municipalities. Twenty-eight test files mention those kommune
   numbers or names, but the rest are literals in fixtures and assertions and are unaffected.
6. The Azure demo is unaffected: public mode has an explicit config in its state dir, and never
   shows a first-run dialog (v3.4 spec A5).

## Part B — bransje and nøkkelord config

Security model unchanged and inherited: loopback bind, Host allowlist, writes need `X-Hugin: 1`,
no CORS, and public mode refuses every non-GET under `/api` in `Security.cs` before any handler
runs.

1. **`GET /api/config/focus`** — `{ naeringskoder: [...], keywords: [...] }`, read fresh from
   hugin.json through `HuginConfigFile`.
2. **`PUT /api/config/focus`** — accepts the same two lists.
   - Codes are validated on **format only**: two digits, optionally `.` plus one to three digits
     (`62`, `58.2`, `64.19`). Brreg has no "is this code real" endpoint, and a nonexistent code
     simply returns zero units — the preview in B3 is where that surfaces, honestly, before the
     save.
   - Both lists are trimmed, de-duplicated case-insensitively, and order is preserved.
   - **Bounded**: at most 50 codes and 200 keywords, each at most 40 characters. Over the limit is
     a 400 naming it. Nothing enforces this today, and a pasted 500-keyword list would slow every
     feed page for no gain while 200 codes would multiply Brreg requests per kommune chunk.
   - **Empty `naeringskoder` is a 400.** Brreg ignores an empty `naeringskode` filter and answers
     with every unit in the country — the same shape of trap `/api/config/discovery` already
     guards for kommunenummer.
   - **Empty `keywords` is legal**: `AdFilter.Matches` reads it as "everything in the region",
     which is a coherent choice for a small kommune. The UI says so rather than blocking it.
   - Writes go through the same **read-modify-write on the raw JSON document** as
     `WriteDiscovery`: re-read hugin.json, drop every case-variant spelling of the two keys, write
     the canonical ones, back up to `hugin.json.bak`, then temp-file + atomic replace. `categories`,
     `navToken`, `linkouts` and any hand-added field round-trip untouched.
   - Refactor `HuginConfigFile` so discovery and focus share one private
     `WriteKeys(IReadOnlyList<string> keys, Action<JsonObject> apply)` — two copies of the
     backup/atomic-replace dance is one copy too many.
3. **`GET /api/config/focus/preview?nace=<code>`** — the count query, against the *current*
   scope: `enheter` and `underenheter` with `size=1`, reading `page.totalElements`, plus
   `naeringskode1.beskrivelse` from the first hit for the display name. Returns
   `{ code, name, units }`; `units: 0, name: null` for a code nothing matches.
   - **The code is validated before it is used, not only on save.** `^\d{2}(\.\d{1,3})?$`, then
     URL-encoded into the Brreg query. Without this, `?nace=62%26size=1000` appends caller-chosen
     Brreg parameters to Hugin's own request.
   - **Requires `X-Hugin: 1`, even though it is a GET.** This endpoint reads to the browser but
     *acts* outward: it makes two Brreg calls. GETs are exempt from the write guard, and the Host
     allowlist passes any request a browser sends to `localhost:5111` — so without the header, any
     page the user happens to be visiting can drive Brreg traffic through Hugin in a loop with a
     `no-cors` fetch. `Security.cs` grows a small named allowlist of side-effecting GETs rather
     than a blanket rule.
   - **Refused with 403 in public mode, explicitly in the handler.** The write guard does not
     cover GETs, and leaving it open would let a demo visitor drive outbound Brreg traffic from
     the F1 instance. Test in `PublicModeEndpointTests`.
   - Two Brreg requests per call. The client debounces, and caches per code **keyed by the current
     scope**, clearing the cache when coverage is saved — a cached count from the old kommuner is
     a wrong number, not a stale one. Unreachable Brreg degrades to "kunne ikke hente antall" and
     the code can still be added.
4. **Curated default + "Legg til anbefalte".** The eight codes above become
   `HuginConfig.Naeringskoder`'s default, in `Hugin.Core` beside the keyword list, each with a
   one-line comment saying why it is there. In Settings, "Legg til anbefalte" offers exactly the
   codes not already configured and previews the total they add before saving.
5. **Settings UI — a Fokus card under Dekning**, mirroring `CoverageSection` and the v3.4.1
   patterns: Save disabled until the form settles, `useAnnounce` for the live region,
   `useReadOnly` disabling everything in demo mode, error text in Norwegian.
   - *Bransjer*: one row per code (code · name · unit count · remove), an add field that previews
     before it commits, and the "Legg til anbefalte" button. A resolved preview is **announced**
     ("63 · Databehandling, hosting og portaler — 45 bedrifter"); an async number that only exists
     visually is invisible to a screen reader. Adding a code that is a prefix of one already in
     the list, or vice versa (`62` beside `62.010`), warns that the narrower one is already
     covered — it is redundant Brreg work, not an error.
   - *Nøkkelord*: chips with add and remove. Each remove control is a `<button>` named for its
     chip ("Fjern nøkkelord «utvikler»"), and removing the last chip moves focus to the add field
     rather than letting it fall to `<body>`. **No count preview** — NAV's feed cannot be counted
     by title without walking it, so a number here would be a guess. The label states that the
     change applies to ads that arrive from now on.
   - Every new remove control is at least 44 × 44 px. The dashboard is desktop-first, but the demo
     is public and reached from phones.
6. **Semantics, stated in the UI and not only here.**
   - Bransjer take effect on the **next ordinary sync**: `SyncBrregAsync` re-queries every
     configured code per kommune chunk, so a widening needs no backfill and no migration.
   - Keywords only affect ads that arrive **after** the change. Widening does not retroactively
     find past ads; that needs the full backfill in Part C, and even then NAV returns closed ads
     as content-stripped stubs, so only open ads come back.
   - Narrowing never deletes rows — companies keep their last-seen date by design, and simply
     stop being refreshed.
7. **Saving and syncing.** One Save button, two behaviours, because the two lists differ:
   a changed `naeringskoder` **auto-syncs immediately**, exactly as a coverage change does since
   v3.4 — a bransje widening means nothing until a Brreg pass runs. A change to `keywords` alone
   does **not** trigger a sync; the confirmation line says the change applies to ads from the next
   sync onward, and points at the full backfill in Part C for past ones. Leaving this unstated
   would get it implemented one way and reviewed the other.

## Part C — full NAV backfill from the dashboard

Keyword editing is close to pointless if the only way to act on a widening is the CLI.

1. **`POST /api/sync?full=1`** → `SyncRunner.TryStart(full: true)` → `SyncAsync(fullNav: true)`.
   Without the parameter the endpoint behaves exactly as today. A sync already running still
   answers 409; `MaxPagesFullSync` (20 000) stays the ceiling.
2. **Confirmed in the UI**, through the existing `ConfirmDialog`: the walk takes minutes and the
   dialog says so, together with the honest limit — closed ads come back stripped, so a backfill
   recovers open ads only.
3. The progress heartbeat already exists (`onNavPage`, surfaced by `SyncHeader`); the button just
   needs to leave the header polling alone. `SyncHeader`'s polling must stay
   identity-independent — the v3.2 trap.

## Part D — reset

Two levels, both in a **Nullstilling** section at the bottom of Settings, danger-styled, each
behind `ConfirmDialog`, both disabled in read-only mode. `POST /api/reset` with
`{ mode: "scope" | "all" }` — a write, so the header guard and the public-mode 403 cover it
without new code.

1. **`mode: "scope"` — nullstill dekning.** Clears `municipalities`, `fylker` and `allOfNorway`
   in hugin.json through the same read-modify-write path. Keeps the database, keeps bransjer and
   nøkkelord (they are domain knowledge, not geography — Part A's line). The response tells the
   client to call `resetFocus()`, and with `scopeConfigured` now false (A3) the first-run dialog
   opens on the next render. This is the "I moved" path: choose new kommuner, sync, done. Old
   companies linger unrefreshed, which the confirm dialog says in one sentence.
2. **`mode: "all"` — start på nytt.** Everything from "scope", plus the data, in exactly three
   ordered steps. **SQLite refuses both `VACUUM` and `VACUUM INTO` inside a transaction**, so
   steps 1 and 3 must run with no `BeginTransaction` open — a spec that says "truncate in a
   transaction, then VACUUM" produces code that throws after the user has confirmed a destructive
   action.
   - **Step 1 — snapshot, no transaction open.** SQLite's own consistent-copy mechanism:
     `VACUUM INTO 'hugin.db.reset-<yyyyMMdd-HHmmss>.bak'` beside the db. A plain file copy of a
     live WAL database is not safe; this is. The filename **must keep the literal `hugin.db`
     prefix**, so the `hugin.db*` patterns that already keep the database out of git and out of
     the release zips catch the snapshot too — it is a full copy of the pipeline, notes and
     starred companies. The path is reported in the response and shown in the UI, so the user
     knows a copy of their job search now exists on disk.
   - The path is interpolated into SQL, because `VACUUM INTO` takes a string literal: **double
     every `'` in it** and refuse a resolved path containing a newline or NUL. `C:\Users\O'Brien\`
     is an ordinary Windows path.
   - **Step 2 — delete rows in one transaction, then commit.** Not the file: the API process holds
     the database open, and truncating avoids the file-lock dance entirely while keeping
     `__EFMigrationsHistory` intact. Wipe `Companies`, `Ads`, `Pipeline`, `ReviewMarks` and the two
     `SyncStates` rows named below.
   - **Step 3 — `VACUUM` after the commit**, again with no transaction open.
   - **`SyncStates` is deleted selectively — `brreg` and `nav` only.** The row `sources-seed` is
     the marker that stops `HuginDbInitializer` re-importing the default sources and the config
     linkouts, and its own comment says deleting sources by hand "must not resurrect the defaults
     on the next launch". A blanket `DELETE FROM SyncStates` would resurrect them.
   - **`Sources` and `Kommuner` are kept.** Sources are links the user wrote, in the db since
     v3.2; the kommune register is a national name lookup that would only be re-fetched.
   - **Refused with 409 while a sync is running** (`SyncRunStatus.Running`) — wiping tables under
     a sync in flight is not a state worth designing for.
   - The confirm dialog names exact counts from `StatusDto` ("1 037 bedrifter, 283 annonser,
     13 pipeline-oppføringer") and links to Eksport first. The pipeline is the only unrecoverable
     loss — companies and ads come back on the next sync, applications do not.
   - **One dialog, not two.** The extra certainty comes from a typed confirmation field inside the
     same `ConfirmDialog` (type `NULLSTILL` to enable the confirm button) — a second nested
     `<dialog>` would break the native focus return that the current component gets for free.
     `ConfirmDialog` grows a `variant: 'danger'` prop, because today its confirm button is
     `btn-primary` and a destructive action must not be styled as the recommended one. Cancel
     keeps first position, as it already has.
   - The control is disabled while the request is in flight. A double-click otherwise writes a
     second snapshot and re-wipes an already-empty database.
3. **Not in this wave**: a CLI `hugin reset`. Noted as a seam.

## Part E — docs and release

1. **README**: the "hand-edited until v3.5" line becomes the honest split — dekning, bransjer and
   nøkkelord in the UI; `categories`, `navToken` and `linkouts` hand-edited. Document the reset
   and the full-backfill button in the dashboard section, and add one line to the CLI section
   saying a fresh install has no coverage until it is chosen (dashboard, or `municipalities` by
   hand).
2. **v3.4 spec header**: rewrite the arc sentence so the repo stops promising adaptability to
   other fields, pointing to this spec and the developer-only decision.
3. **Release notes name one behaviour change**: an install whose config *omits* `naeringskoder`
   inherits the new eight-code default and widens on its next sync. A config that pins `["62"]`
   — mine does — changes nothing until "Legg til anbefalte" is clicked.
4. **Release v3.5.0** with both zips, publish rebuilt and smoke-tested against the real install:
   dialog behaviour on a config with no kommuner, a bransje widening picked up by the next sync,
   both reset levels, and a full backfill.

## Part F — testing

- `HuginConfigFile`: focus round-trip preserves `categories`/`navToken`/`linkouts`; case-variant
  keys (`Keywords` beside `keywords`) are dropped before writing; a failed write leaves the
  original and the `.bak` intact.
- `PUT /api/config/focus`: bad code format → 400 with the offending code; empty `naeringskoder`
  → 400; empty `keywords` → 200; duplicates collapsed; over the 50/200/40 caps → 400 naming the
  limit.
- `GET /api/config/focus/preview`: counts parsed from a fixture; Brreg failure degrades; **403
  without `X-Hugin`**; 403 in public mode; a code failing the regex → 400 and **no outbound call**
  (asserted against the fake Brreg client, which is the point of the finding).
- Saving focus: a changed `naeringskoder` starts a sync; a keywords-only change does not.
- Part A: `SyncBrregAsync` with no scope returns the "Ingen dekning valgt" result; `StatusDto`
  reports `scopeConfigured` both ways; Esc with empty defaults fetches nothing
  (`BootSyncTests`).
- Part C: `POST /api/sync?full=1` reaches `SyncAsync(fullNav: true)`; 409 while running.
- Part D: scope reset clears only the three discovery keys; `all` wipes the four tables, keeps
  `sources-seed`, keeps `Sources`, writes the snapshot file, and 409s while a sync runs. A
  regression test asserts the default sources are **not** re-seeded after a full reset, and one
  asserts the snapshot filename starts with `hugin.db` (the gitignore and packaging filters depend
  on it). A path containing `'` round-trips instead of throwing.
- Web (Vitest, following `CoverageFields.test.tsx`): both Fokus sections, the preview state
  machine including the scope-keyed cache, the typed-confirmation gating on the hard reset, focus
  landing on the add field when the last chip goes, the announcement of a resolved preview, and
  read-only disabling every new control.

## Out of scope, and known seams

- **No cleanup of out-of-scope rows.** Dropping a kommune leaves its companies behind — dropping
  Larvik on 2026-09-09 left 423 rows I deleted by hand. A "rydd bort" action needs a parent-chain
  caveat (a Larvik parent held a unit outside the scope), and the reset in Part D covers the case
  that actually matters. Deliberately not built.
- **Evidence-driven bransje suggestions** — see the rejection above; revisit once live syncs have
  accumulated employer orgnrs.
- **No keyword preview** — not measurable against NAV's feed.
- **`categories`, `navToken`, `linkouts`** stay hand-edited; `categories` deliberately so.
- **No CLI reset.**
- **No EF migration in this wave.** Config and UI only.

## Stress-test record (2026-09-09)

Four lenses run against the first draft of this spec; all eleven proposed changes are folded in
above. What it caught:

- 🔴 **The reset's wipe sequence could not run as written.** SQLite refuses `VACUUM` and
  `VACUUM INTO` inside a transaction, and the draft said "truncate in a transaction, then VACUUM"
  — it would have thrown on the first reset, after the user confirmed a destructive action. Now
  three explicitly ordered steps (D2).
- 🟠 **The preview was an unauthenticated GET with an outward side effect.** GETs skip the write
  guard and the Host allowlist passes anything a browser sends to `localhost:5111`, so any page
  the user visited could loop Brreg calls through Hugin. Now requires `X-Hugin`, validates the
  code before building the URL, and URL-encodes it (B3).
- 🟠 **`VACUUM INTO '<path>'` is interpolated SQL** — a path containing `'` breaks or injects.
  Now quoted and validated (D2).
- 🟠 **"Does saving trigger a sync?" was unspecified**, and the two lists want different answers.
  Now stated (B7).
- 🟠 **Empty kommune defaults dead-ended the CLI**, which has no first-run dialog. Now an
  actionable message plus a README line (A2, E1).
- 🟠 **Three a11y gaps**: the async preview count was never announced, chip remove buttons had no
  names or focus destination, and "a second explicit confirmation" would have become a nested
  dialog that breaks the native focus return. Now one dialog with a typed field, a `danger`
  variant on `ConfirmDialog`, named buttons, and a focus rule (B5, D2).
- 🟡 **The snapshot is a full copy of the pipeline** — the `hugin.db` filename prefix is now a
  requirement, not a coincidence, so existing ignore and packaging filters catch it (D2).
- 🟡 List-size caps, in-flight disable on the reset control, scope-keyed preview cache, a prefix
  warning for redundant codes, the empty-state announcement, 44 px targets, and a release-note
  line for configs that omit `naeringskoder` (B2, B3, B5, D2, E3).

Considered and rejected: keyword injection into the NAV feed URL (verified — keywords never reach
a URL, `AdFilter` matches titles locally); focus return after the confirm dialogs (native
`<dialog>` handles it); CSRF on the new writes (the blanket `X-Hugin` guard already covers every
non-GET); rate-limiting the preview beyond the header and the cache (over-engineering for a
loopback tool); deleting the db file instead of its rows (accepting a larger file until `VACUUM`
rather than fighting a lock the running process holds).
