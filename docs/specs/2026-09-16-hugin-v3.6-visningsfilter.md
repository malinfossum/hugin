# Hugin v3.6 — hierarchical Visningsfilter (several fylker and kommuner)

2026-09-16. The display filter ("Visningsfilter" in Settings, the lens the dashboard and
Bedrifter look through) is a single fylke plus a single kommune. Dekning, the discovery scope
it sits on top of, has been several kommuner in several fylker since v3.4.1. So the filter
cannot express the coverage it filters: with Dekning = Hamar, Gjøvik, Lillehammer, Ringsaker,
the lens is either all of Innlandet (46 kommuner, most of them empty) or one town.

This wave makes the lens hierarchical: tick several fylker, and under each fylke tick the
kommuner that matter. It also removes the second, single-select copy of the filter that
Bedrifter carries, so there is one place that edits the lens and every view reads it.

Nothing on the server changes. The lens is, and stays, a per-browser preference in
`localStorage`; `hugin.json`, the API and the CLI are untouched.

## Decisions locked (2026-09-16)

1. **Hierarchical, not flat.** A region is one fylke with an optional narrowing to kommuner in
   that fylke. Several regions make a filter. This mirrors how the picker reads: fylke rows,
   kommuner underneath.
2. **Full register in the picker.** All 15 fylker from `FYLKER`, every kommune from
   `/api/kommuner`. Not "only what has data" — the list must not change under me when the
   database does.
3. **Summary in the card, picker in a dialog.** The Settings card shows the chosen regions as
   chips and a «Velg områder …» button; the tall list only exists while editing. Settings and
   Bedrifter stay as short as they are today.
4. **Bedrifter shows, Settings edits.** Bedrifter's own fylke/kommune selects go. It renders the
   same chips read-only with a link to Settings. Search and the website filter stay.
5. **«Bruk» applies, «Avbryt» discards.** The dialog works on a draft, like Dekning's Save.
   Chip ✕ in the card applies immediately, like the category tick boxes do today.
6. **A v1 filter migrates, never resets.** Whatever the browser stored under the old schema
   is converted on read and re-saved. Nobody re-answers the first-run dialog because of this.
7. **Larvik is not a test case.** It left config and db on 2026-09-09. Examples use Innlandet
   and Vestfold as a whole.

## Part A — model

### A1. Schema v2

`hugin-web/src/focus.tsx`:

```ts
export interface Region {
  /** Two-digit fylkesnummer, a key in FYLKER. */
  fylke: string
  /** Four-digit kommunenummer in that fylke. Empty = the whole fylke. */
  kommuner: string[]
}

export interface Focus {
  /** Empty = all of Norway. */
  regions: Region[]
  categories: string[]
}
```

Stored as `{ v: 2, regions, categories }` under the existing key `hugin-focus`.

**Normalised order.** `regions` are sorted by fylke number and each `kommuner` list by
kommune number. `saveFocus` normalises before writing, and the A3 migration writes normalised
output, so two equal filters are equal as JSON and chips never reorder because of tick order.
Display order inside a chip is by kommune *name* (`nb`), which is a rendering concern only.

`focus === null` keeps its meaning: unanswered, first-run dialog opens. `regions: []` is an
answer ("everything").

### A2. Validation on read (`loadFocus`)

Returns `null` (as today, for the same reasons) when: the key is missing, storage throws, JSON
is invalid, `v` is not 1 or 2, or any field is malformed. For v2, malformed means: `regions` is
not an array of `{ fylke: string, kommuner: string[] }`; a `fylke` is not a key in `FYLKER`;
two regions share a fylke; a kommune is not exactly four digits (`/^\d{4}$/`) or does not start
with its region's fylke number. The digit check is cheap and keeps anything that is not a
kommunenummer out of state, `title` attributes and accessible names alike. Kommuner
are not checked against the register — a kommune that later leaves the register stays in the
filter harmlessly and shows in its chip by number.

### A3. Migration from v1

A stored `{ v: 1, fylke, kommune, categories }` that passes the v1 checks converts:

| v1 | v2 `regions` |
|---|---|
| `fylke: null, kommune: null` | `[]` |
| `fylke: '34', kommune: null` | `[{ fylke: '34', kommuner: [] }]` |
| `fylke: '34', kommune: '3403'` | `[{ fylke: '34', kommuner: ['3403'] }]` |

The converted value is written back as v2 during `loadFocus` (best-effort, swallowed on
storage error, like `saveFocus`). A v1 record that fails the v1 checks returns `null`, as before.

### A4. Matching

`adMatchesFocus(ad, focus)` keeps its signature and its two hard rules: `focus === null`
matches everything; a tracked ad (`pipelineStatus` set) always matches. Region rule:

```
regionOk = regions.length === 0
        || ad.kommune === null                         // fail open on missing data
        || regions.some(r => fylkeOf(ad.kommune) === r.fylke
                          && (r.kommuner.length === 0 || r.kommuner.includes(ad.kommune)))
```

Category rule unchanged. A new `regionMatches(kommune, regions)` carries the region rule so
Bedrifter can apply it to companies (which have no pipeline bypass and no category).

### A5. First-run seed

`toFocusSeed(draft, categories)` in `coverage.ts` maps the coverage draft without loss, built
in a `Map<fylke, Region>` in this order:

1. `draft.fylke` with `draft.kommuner` → one region, kommuner as ticked (empty = whole fylke).
   `draft.fylke === ''` (all of Norway) → `regions: []`, and nothing below runs.
2. `draft.others.fylker` → one whole region each (`kommuner: []`).
3. `draft.others.municipalities` → for each, `fylkeOf(number)`: no region for that fylke →
   create a narrowed one; an existing narrowed region → merge the number in (deduped); an
   existing whole region → absorbed, nothing added (a whole fylke already contains it). A
   number whose fylke is `draft.fylke` therefore lands in the main region, even though
   `effectiveDraft` should never put one there.

The result is normalised per A1.

This replaces the current collapse ("several kommuner → fylke only"), which was the only
reason a fresh install saw more than it asked for.

## Part B — components

### B1. `AreaPickerDialog` (new, `components/AreaPickerDialog.tsx`)

Props: `open`, `value: Region[]`, `kommuner: KommuneDto[] | null | undefined`,
`onApply(regions)`, `onCancel()`. The dialog never fetches: `kommuner` follows the
`CoverageFields` contract (undefined = still loading, null = register unreachable, list =
ready) and is owned by the view (B3). Same dialog conventions as `FirstRunDialog`:
`role="dialog"`, `aria-modal`, labelled heading that takes focus on open, focus returns to the
button that opened it. The dialog body scrolls inside the viewport; the footer stays visible.

**Esc.** Inside the search field with a non-empty query, Esc only clears the query (and stops
propagating — Chrome clears `type="search"` on Esc, and the keydown would otherwise reach the
dialog and throw the draft away). Esc on an empty search field, or anywhere else in the
dialog, cancels.

Content, top to bottom:

- **Search** (`<input type="search">`, labelled «Søk fylke eller kommune»). Case- and
  diacritic-insensitive prefix/substring match on fylke names and kommune names. While the
  query is non-empty: fylke rows without any hit are hidden, rows with hits are expanded, and
  only matching kommuner are listed. Clearing the query restores the rows and the user's own
  expand state. Result count is announced through the live region («12 treff»).
- **One row per fylke**, all 15 in `FYLKER` order (number order, as the map is declared). Two
  controls per row, each named: a tick box labelled with the fylke name, whose count text
  («4 av 46 valgt» / «hele fylket» / «46 kommuner») is attached with `aria-describedby`; and a
  disclosure button named «Vis kommuner i {fylke}» / «Skjul kommuner i {fylke}» with
  `aria-expanded` and `aria-controls` pointing at the kommune list. The row is a ≥44 px target.
- **Expanded row**: the fylke's kommuner from `kommuner` (sorted `nb`), each a tick box in a
  responsive grid — one column on phone, three from `768px`. Each kommune row is a ≥44 px
  target, as `CoverageFields` already does.
- **Footer**: «Avbryt» and «Bruk».

Tick semantics on the draft:

- Tick a fylke → region `{ fylke, kommuner: [] }` (whole fylke). If kommuner were ticked
  under it, they are cleared — the fylke tick means "all", and the row count says so.
- Untick a fylke → region removed, its kommuner with it.
- Tick a kommune → if the fylke has no region, one is created; the kommune is added to it.
  The fylke tick box shows the mixed state (`aria-checked="mixed"` via `indeterminate`).
- Untick the last kommune under a fylke → the region becomes a whole fylke, and the fylke tick
  goes from mixed to checked. Removing the fylke is the fylke tick box, not the last kommune.
  (Dropping the region on the last untick would make "all of Innlandet" unreachable by
  unticking, and unticking should never widen the filter.)

Register unreachable (`kommuner === null`): rows still list and tick as whole fylker, the
disclosure is disabled, and the same hint Dekning shows (`coverage.kommunerUnavailable`)
appears once under the search box. Existing kommune narrowings in the draft are preserved
untouched and their count still reads «n valgt», by number if names are unknown. «Bruk» stays
enabled. While `kommuner === undefined` the disclosures are disabled too, without the hint.

`open` false renders nothing. The draft is seeded from `value` each time the dialog opens.

### B2. `RegionChips` (new, `components/RegionChips.tsx`)

Props: `regions: Region[]`, `kommuneNames?: ReadonlyMap<string, string>`, `onRemove?(fylke)`.

Renders `<ul>` of chips, one per region, in the order stored: «Innlandet: Hamar, Gjøvik,
Lillehammer, Ringsaker» or «Vestfold: hele fylket». Names come from `kommuneNames` when the
caller has them, falling back to the number. With `onRemove`, each chip carries a ✕ button
labelled «Fjern Innlandet». Empty `regions` renders the single text «Hele Norge» (no chip, no
✕). More than four kommuner in one chip collapse to «Hamar, Gjøvik, Lillehammer +3» with the
full list in the chip's `title` and in its accessible name.

Each ✕ is a ≥44 px target.

**Focus after ✕.** The button that had focus unmounts with its chip, so the caller moves focus
by hand through a pending-focus ref applied in an effect after the list re-renders (the
`FristerList` pattern): to the next chip's ✕, else the previous chip's ✕, else «Velg områder
…». Focus never falls to `<body>`.

### B3. Settings card

`views/SettingsView.tsx`, the section labelled `settings.focusHeading`:

hint → `RegionChips` (with ✕, applied at once through `setFocus`) → «Velg områder …» →
categories fieldset (unchanged) → «Nullstill filter» (unchanged: `resetFocus`, focus → null,
first-run dialog returns).

The view owns the one `/api/kommuner` fetch: lazily on first render of the section
(replacing today's lazy `/api/companies` fetch, which only existed to fill the kommune select),
held as `KommuneDto[] | null | undefined` and passed to both `RegionChips` (as a name map) and
`AreaPickerDialog`. If the fetch fails the chips show numbers and the dialog degrades per B1;
nothing else changes. No fetch happens inside the dialog, so closing it mid-request cannot
update an unmounted component.

**Announcements.** Chip ✕ and dialog «Bruk» both announce `settings.focusUpdated`, as every
Visningsfilter change does today. «Avbryt» announces nothing.

The `handleFocusFylkeChange` / `handleFocusKommuneChange` handlers and the two selects go.

### B4. Bedrifter

`views/BedrifterView.tsx`: the fylke and kommune selects and `writeBackRegion` go. In their
place, above search: `RegionChips` read-only (no ✕) followed by a link «Endre i Innstillinger»
(a button styled as a link, wired through a new `onOpenSettings` prop that App binds to
`switchView('settings')`, the same way `onOpenCompany` is passed today). Kommune names for the chips come from the companies already loaded
(`kommuneNavn`), so this view needs no extra fetch. The chips receive `focus?.regions ?? []`,
so a null focus (first-run dialog dismissed for the session) reads «Hele Norge» — which is
what `adMatchesFocus(null)` does. The company list filters with
`regionMatches(c.kommune, focus?.regions ?? [])`; a company without a kommune fails open, as
ads do.

The write-back that made a Bedrifter select answer the first-run question is gone with the
selects; the first-run dialog is the answer now, as it is for everything else.

### B5. First-run dialog

No visible change. `toFocusSeed` (A5) produces regions; the dialog's Start path is otherwise
untouched.

### B6. Strings

New `nb`/`en` keys: dialog title and search label, «Velg områder …», «Bruk», «Hele Norge»,
«hele fylket», «{n} av {total} valgt», «{n} kommuner», «Fjern {fylke}», «{n} treff», «Endre i
Innstillinger», the «+{n}» chip suffix. `focus.allOfNorway` and `settings.focusUpdated` stay.

## Out of scope, and known seams

- The server-side Dekning is not touched. A region in the lens outside Dekning simply shows
  nothing; the picker does not warn about it. (A "not in your coverage" hint is a possible
  follow-up, not this wave.)
- Kommune merges/splits in the register: a stored number that disappears shows as a number in
  its chip until the user unticks it. No automatic remap.
- The category half of the filter is unchanged, including its `String.includes` matching.
- The lens stays per browser. Two browsers, two lenses — as today.

## Stress-test record (2026-09-16)

Four lenses run against the first draft; all nine proposed changes are folded in above. What it
caught:

- 🟠 **B1 and B3 disagreed on who fetches `/api/kommuner`** — the dialog *and* the view, with
  an unmount race in the dialog version. Now the view owns the one fetch and hands the dialog
  and the chips the `CoverageFields` contract.
- 🟠 **Esc in the search field threw the draft away.** Chrome clears `type="search"` on Esc and
  the keydown still reached the dialog. Esc now clears first, cancels second.
- 🟠 **Chip ✕ dropped focus to `<body>` on a middle chip and announced nothing.** Focus moves
  next → previous → «Velg områder …»; ✕ and «Bruk» announce `settings.focusUpdated`.
- 🟡 Regions were stored in tick order, so chips reordered and equal filters differed as JSON
  → normalised order in `saveFocus` and migration.
- 🟡 A5 did not say what an «other» municipality in an already-present fylke does → map-based
  build with merge and absorb.
- 🟡 `RegionChips` with a null focus was undefined → Bedrifter passes `focus?.regions ?? []`.
- 🟡 The fylke row's two controls had no names, and targets were only sized for kommune rows
  → both named, everything ≥ 44 px, dialog body scrolls with the footer visible.
- 🟡 Kommune strings were only prefix-checked → `/^\d{4}$/`.

Considered and rejected: mixed-state fylke click means "whole fylke" (native checkbox
behaviour); duplicate-fylke regions → `null` rather than merge (hand-edited storage only, same
policy as every malformed record); «Nullstill filter» reopening the first-run dialog (v3.5
behaviour, and «Velg områder …» → untick all → «Bruk» is the non-destructive route to all of
Norway); obsolete fylke numbers in a v1 record (Hugin has only existed with the 2024 register);
Bedrifter chips naming kommuner from companies while Settings uses the register (accepted to
keep Bedrifter fetch-free); no "outside your Dekning" hint in the picker (out of scope).

## Post-implementation corrections (2026-09-16)

1. `Region` and the region helpers live in `hugin-web/src/regions.ts`, not `focus.tsx` (A1): the
   picker and the chips depend on the type without depending on storage. `focus.tsx` imports it.
2. The `/api/kommuner` fetch and the dialog state live in `components/VisningsfilterSection.tsx`,
   a Settings section component extracted the way `CoverageSection` was — B3's "the view owns
   the fetch" holds, one level down.
3. The Bedrifter «Endre i Innstillinger» control is a ghost button, not a link-styled button
   (B4): the design system has no link-styled button and one was not worth adding.
4. The README had no «Visningsfilter» paragraph (Part D); one sentence was added to the Web
   dashboard paragraph instead.
5. Under a whole fylke the picker shows its kommune boxes unticked (the Dekning reading, «ingen
   valgt = hele fylket»); ticking one narrows. B1 did not say which way this reads.
6. The plan's picker test expected «1 treff» for the query «ham», but the fixture list includes
   Lillehammer, which contains «ham» mid-word. The spec's «prefix/substring match» (B1) is
   binding, so the search matches substrings and the test was corrected to expect Hamar and
   Lillehammer, «2 treff».
7. Two tests in `App.test.tsx` that the plan did not list had to be rewritten: one asserted the
   removed `#settings-focus-fylke` select, the other the v1 storage shape. Both were replaced
   with equivalent end-to-end assertions (the seed is now observed through the Bedrifter
   filter).
