# Hugin v3.7.3: a fictional demo seed

2026-10-08. The public demo tracks three real IT employers in its pipeline. They were picked to
stay clear of my own job search, and they turned out to be too close to it after all. In an
area this size, a real IT employer on a public page is too close to my own search to be safe
as «Følger med». A real name under that label reads as my interest, whatever the why-line
says.

This patch replaces the seed with three fictional firms, each with one fictional ad, so the demo
shows the pipeline without pointing at anyone real. The fictional data also lets the demo show
more of the dashboard than the old seed did: one ad close to its deadline, one fresh ad and one
expired ad, across all three pipeline statuses.

## Decisions locked (2026-10-08)

1. **Fictional firms, not the biggest real ones.** Big real employers were considered and
   rejected for the reason above: size does not make a firm neutral here.
2. **Orgnr that can never be real.** Norwegian organisation numbers start with 8 or 9. The seed
   uses `100000001`, `100000002` and `100000003`. The Brreg sync can never overwrite them, and
   no lookup or link can land on a real company.
3. **Names checked against Brreg.** Mjøskode AS, Tindebit AS and Lysbekk Data AS give zero name
   hits in both `/enheter` and `/underenheter` (checked 2026-10-08). The company link falls back
   to a web search for the name, which is harmless when no company carries it.
4. **One ad per firm, one status per firm.** One ad or three is the same work: the cost is the
   mechanism, not the data.
5. **Extend `demo-pipeline.json`, not a second file.** One file and one seeder, following the
   pattern already there. Baking the rows into the snapshot db once was rejected: the dates
   would freeze, and within a week the deadline ad would be expired and the fresh ad gone from
   «Nytt siden sist».
6. **Patch release v3.7.3 from `release/v3.7.2`.** Main carries v3.8 wave 1, which is not
   released yet, and the demo should run a released version. The change is merged to main too.

## Part 2: the seed format

Every entry keeps today's fields. Three optional fields are new:

```json
{
  "orgnr": "100000001",
  "status": "active",
  "why": "Demo: fiktivt firma, sporet for å vise pipelinen.",
  "company": { "name": "Mjøskode AS", "kommune": "3403", "nace": "62.010" },
  "ad": { "title": "Fullstackutvikler (.NET/React)", "publishedDaysAgo": 10, "expiresInDays": 3 }
}
```

- `svar` (string, optional): stored on the pipeline row when it is inserted.
- `company` (object, optional): `name` non-empty, `kommune` four digits, `nace` in the form
  `NN.NNN`.
- `ad` (object, optional, requires `company`): `title` non-empty, `publishedDaysAgo` an integer
  of 0 or more, `expiresInDays` an integer that may be negative.

Validation follows the existing rule: an invalid entry is skipped whole, with one warning line
naming it. New problems:

- a `company` block on an orgnr that starts with 8 or 9 (the seeder must never write over a
  real company);
- an `ad` block without a `company` block;
- an empty name or title, a malformed kommune or nace, or `publishedDaysAgo` below 0.

Entries without the new blocks behave exactly as today, so a real orgnr from the snapshot still
works.

## Part 3: what the seeder does

The seeder still runs at boot and after every sync, before the snapshot copy-back, and only in
public mode. For each valid entry, in this order:

1. **Company.** If the entry has a `company` block, write the company on every run: name,
   kommune and nace from the block, not a branch, no parent, no website. On insert, `FirstSeen`
   is set 60 days back so the fictional firms never show up as newly discovered companies;
   later runs keep it. Refreshing every run makes the seed file the truth for its own fictional
   rows (a corrected name or kommune lands on the next run), and the 8-or-9 guard in Part 2 is
   what keeps this from ever touching a real company.
2. **Ad.** If the entry has an `ad` block, write the ad on *every* run, keyed on the fixed
   `FeedId` `demo-<orgnr>`:
   - `Published` and `FirstSeen` = now minus `publishedDaysAgo` days;
   - `Expires` = 23:59:59 UTC on the UTC date `expiresInDays` days after today's UTC date.
     `AdOverviewService` counts `DaysLeft` as whole UTC dates (`e.UtcDateTime.Date - today`), so
     this gives exactly `expiresInDays`. "Local end of day" would be wrong here: the Azure
     container runs in UTC and my machine in Europe/Oslo, so the same seed would give different
     counts;
   - `IsActive` = `expiresInDays >= 0`;
   - employer name and orgnr from the entry, kommune from the `company` block, category
     `IT / Utvikling`, no `SourceUrl`;
   - `Hidden` and `LinkedOrgnr` are Hugin-owned and left as they are on an existing row.

   The seeder writes these fields itself. It does **not** reuse the feed upsert: that path keeps
   the first `FirstSeen` and falls back to the old value for null fields, which would stop the
   dates from rolling and keep a stale `Expires`.
3. **Pipeline row.** Unchanged rule: insert once if missing, never update. `svar` goes in with
   the insert. An entry with no company row (no `company` block and the orgnr not yet synced)
   is still skipped with a warning and retried after the next sync.

**A failing entry never stops the boot.** The seeder is awaited during startup, so an
exception from one of the new writes would take the whole demo down. Each entry is handled on
its own: a database exception is logged as a warning naming the orgnr, and the seeder moves on
to the next entry. Because every write is idempotent, a half-written entry (company in, ad not)
is completed on the next run.

The dates stand still between syncs, so Mjøskode's deadline can drift from 3 to 2 days before
the next sync moves it back. I accept that. The only sync code that touches a demo ad is the
expiry sweep (`DeactivateExpiredAsync`), which closes Lysbekk Data's ad, which is what the seed
asks for anyway. NAV feed upserts are keyed on NAV's UUIDs and never meet a `demo-` id.

## Part 4: the demo banner

The banner says every ad on the page is real («Ekte stillinger og selskaper fra NAV og Brreg»).
With three fictional ads mixed in, that stops being true, and a visitor could go looking for a
Tindebit AS job that does not exist. Both languages change (`demo.banner` in `nb.ts` and
`en.ts`); the old string's em dash goes with the rewrite:

- nb: «Skrivebeskyttet demo. Ekte stillinger og selskaper fra NAV og Brreg for Innlandet, pluss
  tre fiktive firmaer med én fiktiv annonse hver. Pipelinen viser bare de fiktive firmaene.
  Ingen sporing, ingen informasjonskapsler; temavalg lagres bare i din nettleser.»
- en: «Read-only demo. Real job ads and companies from NAV and Brreg for Innlandet, plus three
  fictional companies with one fictional ad each. The pipeline shows only the fictional
  companies. No tracking, no cookies; your theme choice is stored only in your browser.»

The banner element, its role and its place on the page stay as they are.

## Part 5: rollout

1. Build on `feat/demo-fictional-seed` from main, merge to main.
2. Cut `release/v3.7.3` from tag `v3.7.2`. Cherry-pick `958a18e` (the Ward hygiene workflow)
   first, so the release event does not call the removed workbench workflow, then cherry-pick
   the seeder commits. Tag `v3.7.3`, release with both zips, check the assets.
3. Swap the live data, the same procedure as demo spec correction 14: stop the app, download
   `/home/data/hugin.db` and `/home/data/demo-pipeline.json`, run `hugin untrack` on each orgnr
   in the old seed file against the downloaded db with the demo config beside it, upload the db,
   the new seed and the new build, start the app. The `az` steps are mine to run. The order of
   the uploads does not matter: the v3.7.2 build ignores the unknown fields and skips the
   fictional orgnr with a warning (no company row), so a new seed beside an old build seeds
   nothing rather than something wrong.
4. Verify live: `/api/pipeline` lists exactly the three fictional firms with their statuses and
   none of the orgnr from the old seed file, `/api/ads` has the three demo ads with `daysLeft`
   3, 21 and an expired one, the dashboard shows Trenger handling, Frister and Nytt siden sist
   with the fictional ads, the banner shows the new text in both languages, `PUT` still answers
   403.

The old firm names stay in git history. I am not rewriting it: the commits only say the firms
were picked for a demo.

## Part 6: testing

NUnit with `FakeClock`, test first:

- **Parse:** the new blocks and `svar` are read, including a name with «ø» read from a UTF-8
  file. Each new validation problem from Part 2 skips the entry with one problem line, and the
  other entries survive. The 8-or-9 guard has its own fixture that must be rejected.
- **First run:** creates the company, the ad and the pipeline row. Dates match the clock, the
  expired ad is inactive, the deadline is 23:59:59 UTC. With the clock at 23:30 and at 01:30 Oslo
  time (the second one is still the previous day in UTC), `DaysLeft` through
  `AdOverviewService` is exactly 3 for `expiresInDays: 3`.
- **Second run with the clock two days on:** the ad dates have moved, the company keeps its
  `FirstSeen`, and the pipeline row is unchanged.
- **A changed `company` block** is applied on the next run.
- **A failing entry:** with an ad repository fake that throws for one orgnr, `ApplyAsync`
  completes, logs a warning and still seeds the other entries.
- **Hidden flag survives a rerun.**
- **Banner:** `App.test.tsx` asserts the new text in both languages.
- **Old behaviour:** the existing seeder tests stay green unchanged, normal mode seeds nothing,
  and an entry without blocks and without a company row is still skipped.
- **API:** `/api/ads` in public mode returns a demo ad with its `pipelineStatus`.
- **Manual:** run the API locally in public mode against a scratch state dir, never my real db,
  and check the three dashboard cards.

## Stress-test record (2026-10-08)

Applied:

1. **Privacy: the first draft leaked my pipeline.** It said the biggest IT employers in the area
   included firms in my real pipeline. With Brreg's public staff counts, anyone could name them.
   The intro, decision 1 and demo spec correction 14 now say only that real employers here are
   too close to my search.
2. **Banner honesty.** The demo banner called every ad real. Part 4 rewrites it in both
   languages.
3. **Rollout order.** Part 5 states that a new seed beside the old build seeds nothing, and the
   live check now confirms the old orgnr are gone.
4. **Encoding.** The parse test reads «ø» from a UTF-8 file.

Adapted:

1. **Deadlines in UTC, not local end of day.** `DaysLeft` counts UTC dates and the container
   runs in UTC, so a UTC deadline gives the same count everywhere; local end of day would not.
2. **Company rows refresh every run** instead of insert-once. The seed file becomes the truth
   for its own rows, and the 8-or-9 guard is what keeps real companies out of reach.
3. **A failing entry never stops the boot.** Per-entry handling with a warning, healed by the
   next idempotent run. This beats a single try/catch around the whole seeder, which would skip
   the remaining entries.

Considered and rejected:

- **Marking the ad titles «(fiktiv)».** The banner and the why-line already say it, and the ads
  carry no NAV link, so there is no apply path to mislead anyone into.
- **Trademark search on the three names.** They are demo data, not a brand; the Brreg check
  covers the realistic collision.
- **Pipeline rows that follow seed edits.** Insert-once stays, as in the demo spec: a status
  change goes through the swap procedure, so the demo cannot drift by accident.
- **Rewriting git history** to drop the old names. The commits only say the firms were picked
  for a demo.
