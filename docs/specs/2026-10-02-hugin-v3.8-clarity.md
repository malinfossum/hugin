# Hugin v3.8: clarity for a first-time visitor

2026-10-02. An external frontend review said the backend holds up, but a first-time visitor has
to guess what the dashboard is telling them. The cards have titles but no explanation. «Aktiv»
means two different things. The logo goes nowhere, and the page has no footer saying where
the data comes from. Company names in «Nytt siden sist» are dead text. The company list cannot
answer the obvious question: which of these companies are hiring right now?

v3.8 fixes that in four items. A fifth item from the same review (English component names,
`lib/` and `context/` folders) already shipped as PR #33.

1. The logo links home, and a footer shows the version, the repo and the data credit.
2. Every dashboard card gets a one-line description, and the cards are reordered.
3. The «Aktiv» pipeline status is renamed «Følger med» (Watching).
4. The company list gets a «has open ad» filter, and «Nytt siden sist» links each new company
   and counts per place.

The same review led to a parallel contribution from the reviewer: React Router and TanStack
Query, then possibly the company detail as a dialog. This spec is sequenced around that work.

## Decisions locked (2026-10-02)

1. **Two waves, one release.** Wave 1 (items 2 and 3) touches card markup, CSS, i18n and one
   CLI line. It can merge now with only a small rebase for the reviewer. Wave 2 (items 1 and
   4) builds on the router, so it starts after the reviewer's router PR is merged. `App.tsx`
   belongs to that PR until then. Each wave is its own PR. v3.8.0 ships when both have landed.
2. **Rename the label, not the data.** The stored status and API slug stay `active`. So do the
   CLI input (`hugin track <orgnr> active`), the export flag `--include-active` and the JSON
   export. Only text a person reads changes. No migration.
3. **«Aktiv» keeps one meaning: an open ad.** «aktive annonser», «Aktive frister» and the
   export's «Aktiv» ad section stay as they are. After the rename, that is the only thing
   «aktiv» means in Hugin.
4. **Card order: action first, sources last.** Sync strip, Trenger handling, Frister, Nytt
   siden sist, Kilder.
5. **Open-ad counts come from the server.** The alternatives were a client-side join with
   `/api/ads` (a second fetch, with the open-ad rule duplicated in the browser) and a server
   query parameter (the only filter not applied in the browser). Both were rejected.
6. **The version has one source: the git tag.** The publish build stamps it into the API
   assembly, and `/api/status` reports it. Nothing is bumped by hand.

## Part A: wave 1 (now)

### A1. Card order

`DashboardView` renders, top to bottom: `SyncHeader`, `NeedsAction`, `DeadlineList`,
`NewSinceLastVisit`, `SourcesCard`. `NeedsAction` still renders nothing when it has nothing to
show, so on most days `DeadlineList` sits directly under the sync strip.

### A2. One-line descriptions

Each card gets a `<p>` directly under its `<h2>`, styled with the design system's
`.text-muted`. The muted ink is what sets the description apart from the heading (the
"labels look like labels" rule). The description is plain text. It is not wired to the section
with `aria-describedby`: it sits right after the heading, which screen readers already reach in
reading order.

| Card | Key | bokmål | English |
|---|---|---|---|
| Trenger handling | `needsAction.description` | Annonser fra bedrifter du følger med på, med frist innen 7 dager. | Ads from companies you're watching that close within 7 days. |
| Frister | `deadlines.description` | Åpne annonser i området ditt, nærmeste frist først. | Open ads in your area, closest deadline first. |
| Nytt siden sist | `newSince.description` | Bedrifter og annonser som har kommet til siden du sist trykket «Merk som sett». | Companies and ads added since you last pressed "Mark as seen". |
| Kilder | `sources.description` | Registrene Hugin henter fra, og stillingssider du sjekker selv. | The registers Hugin reads from, and job sites you check yourself. |

The sync strip gets no description. It is a status bar with a visually hidden heading, not a
card.

The gap between heading and description follows the card's existing `stack` rhythm. No new
spacing token.

### A3. «Aktiv» becomes «Følger med»

| Where | Before | After (nb / en) |
|---|---|---|
| `status.active` | Aktiv / Active | Følger med / Watching |
| `needsAction.notApplied` | aktiv, ikke søkt / active, not applied | følger med, ikke søkt / watching, not applied |
| `applications.activeHint` | Aktiv-oppføringer tas bare med i eksporten når du velger det. / Active entries are only exported when you opt in. | Bedrifter du følger med på tas bare med i eksporten når du velger det. / Companies you're watching are only exported when you opt in. |
| CLI status label (`Program.cs`, `PipelineStatus.Active`) | aktiv | følger med |
| README feature paragraph | `Active` → `Applied` → `Answered` | `Watching` → `Applied` → `Answered`, with one clause saying the CLI value is still `active` |

The CLI command table in the README keeps `active` as the accepted value, because that is
what you type.

Any test that asserts the old label text changes with it. The tests stay the same otherwise.

## Part B: wave 2 (after the reviewer's router PR is merged)

### B1. Logo links home

The brand in the top bar (`HuginMark` plus the name) becomes a router link to `/`. Its
accessible name is «Hugin, til oversikten» / "Hugin, to the dashboard" (i18n key
`brand.homeLabel`). The name starts with the visible word, so speech input ("click Hugin")
still works. Visually it stays as it is: no underline, and the existing focus ring.
Activating it does exactly what the «Oversikt» nav item does: same focus move, same
per-view scroll memory. It is the same navigation, not a second one.

### B2. Footer

A `<footer>` after `<main>` in the app shell, holding one line that wraps on narrow screens:

- `Hugin v3.8.0`: the version from B3. If the status fetch failed, the version is left out
  and the rest stays.
- `GitHub`: links to `https://github.com/malinfossum/hugin`.
- «Annonser fra NAV · Bedriftsdata fra Brønnøysundregistrene (NLOD)» / "Ads from NAV ·
  Company data from the Brønnøysund Register Centre (NLOD)". «NLOD» links to
  `https://data.norge.no/nlod/no/2.0` in bokmål and `https://data.norge.no/nlod/en/2.0` in
  English (both checked 2026-10-02, HTTP 200). Brreg's Enhetsregisteret API documentation
  names NLOD 2.0 as its licence, and NLOD asks for a source credit. NAV's API terms
  (`arbeidsplassen.nav.no/vilkar-api`, read 2026-10-02) name no licence and ask for no
  credit. That is why the licence sits on the Brreg half only, rather than implying NAV's data
  is NLOD too. NAV's real conditions are met where they already are (the stored deep link,
  and expired ads never shown as open).

External links open in a new tab with `rel="noopener noreferrer"`, like every other external
link in Hugin. The footer is muted, small and centred. It shows in the demo too. Small text
does not mean small targets: each footer link is `inline-flex` with `min-block-size: 44px`,
centred on the line, so the hit area meets the 44 px house bar while the text stays small.

`.app-shell` already sizes its grid rows for the demo banner (PR #18). The footer adds one
`auto` row. It must not push `<main>` down, or take the `1fr` row, on short viewports. Check
at 320 px, 375 px and 1280 px, with and without the demo banner. 320 px is the reflow floor,
and the bokmål credit is the longest line.

### B3. Version plumbing

- **Server:** `Hugin.Api.csproj` sets `<InformationalVersion>dev</InformationalVersion>` and
  `<IncludeSourceRevisionInInformationalVersion>false</IncludeSourceRevisionInInformationalVersion>`.
  The second keeps the SDK from appending `+<commit sha>`.
- **Build:** `build.ps1` and `publish-demo.ps1` read `git describe --tags --always --dirty`
  as their first step, before `npm run build` and before anything else can touch the tree.
  They fall back to `dev` if git fails, and pass `-p:InformationalVersion=<value>` to every
  `dotnet publish` of `Hugin.Api`. That is three calls in `build.ps1` and one in
  `publish-demo.ps1`. A release built on its tag reads `v3.8.0`. A build between tags reads
  like `v3.8.0-2-gabc1234`, which is honest about what it is.
- **API:** `StatusDto` gains `string Version`, read once from the API's own assembly
  (`typeof(Program).Assembly`), `AssemblyInformationalVersionAttribute`. Not the entry
  assembly: under `WebApplicationFactory` the entry assembly is the test host, and the test
  would read the wrong version. It falls back to `dev` when the attribute is missing.
- **Web:** `StatusDto` in `lib/types.ts` gains `version?: string`, optional like
  `scopeConfigured`. The footer reads it from the boot-time status fetch that already exists.
  That is the `readOnly` context today, or the shared status query if the reviewer's TanStack
  Query PR has replaced that fetch. No second request.

Release rule: tag first, then build the zips. That is already the order in the release
routine.

### B4. «Har åpen annonse» filter on the company list

**Server.** `CompanyDto` gains `int OpenAds`. It counts ads where:

- `EmployerOrgnr` equals the company's orgnr (its own ads only; a branch counts its own),
- the ad is open now (`Ad.IsOpenAt(now)`), and
- the ad is not hidden (`Hidden == false`). An ad I hid as irrelevant should not make a
  company look like it is hiring.

`IAdRepository` gains `CountOpenByEmployerAsync(DateTimeOffset now)`, which returns
`IReadOnlyDictionary<string, int>` (orgnr to count) in one grouped query. `CompanyDto.From`
takes that dictionary, and every endpoint that builds a `CompanyDto` passes it:
`/api/companies`, `/api/companies/{orgnr}` (company and branches) and `/api/new`. A company
missing from the dictionary has 0. Public mode needs no extra rule, because the count is open
ads only.

**Web.**

- The filter row in `CompaniesView` gets a select beside the website filter. It is labelled
  «Annonser» / "Ads" and offers «Alle» / "All" and «Med åpen annonse» / "With an open ad".
  It is 44 px tall, on the same row and bottom edge as the other controls.
- Matching is per unit, like the other filters. The existing group logic then shows a group
  when its main unit or any branch has an open ad.
- A row whose group has open ads shows a muted count after the name: «3 åpne annonser» /
  "3 open ads" («1 åpen annonse» / "1 open ad"). The count is the group total (main plus
  branches), because the row stands for the group. Rows with 0 show nothing.
- The filter combines with search, the website filter and the display filter (logical AND).
  It is not persisted, like the website filter.
- The existing result line under the filters («12 bedrifter») gets `role="status"`. Today a
  filter change is silent for a screen reader: the select reads its new value, but nobody
  hears how many companies are left. The element stays mounted and only its text changes,
  so the region exists before the first change. That also fixes the website filter and the
  search for free.

### B5. «Nytt siden sist»: links and counts per place

- Each new company name becomes a router link to `/companies/{orgnr}`. Once the reviewer's
  dialog lands, that opens the dialog. Until then it opens the detail view as today.
- **Closing the detail returns to where it was opened.** Today the detail's own close
  button always goes to `/companies` (`App.tsx`, `onCloseCompany`). Opened from the
  dashboard, that drops me in the company list instead of back where I was. Rule: when the
  detail was opened by in-app navigation, close goes back one step in history, exactly like
  the browser's Back. On a cold deep link (no in-app history), close goes to `/companies` as
  today. Either way, focus returns to the link that opened it. The dashboard stays mounted,
  so the link still exists. This is the same condition the reviewer's dialog already has to
  meet, so it holds whichever lands first.
- Place headings show a count: «Hamar · 3». The visible « · 3» is `aria-hidden`, and a
  visually hidden suffix gives screen readers «Hamar, 3 bedrifter» / "Hamar, 3 companies",
  so the number is read once, not twice. Singular reads «1 bedrift» / "1 company". Ad groups
  use «annonser» / "ads" («1 annonse» / "1 ad").
- New ads are grouped by place the same way, also with counts. `AdDto` gains
  `string? KommuneNavn`, resolved by the same lookup `CompanyDto.From` uses (configured
  municipality name first, then the Brreg kommune register). That means `AdDto.FromAd` takes
  the kommune dictionary at every call site. An ad with no kommune goes under «Ukjent sted» /
  "Unknown place". The ad title keeps its NAV link.
- Group order stays first-seen, as today.

## Part C: testing (tests first, per task)

**Wave 1**
- `DashboardView`: the card headings appear in the order from A1.
- Each card renders its description in nb and en.
- Status label, `needsAction.notApplied` and `applications.activeHint` read «Følger med» /
  "Watching" in their respective tests. A guard test checks that `status.active`,
  `needsAction.notApplied` and `applications.activeHint` in `nb.ts` do not match
  `/\baktiv\b/i`. It names those three keys rather than scanning the file, because «aktive
  annonser» must stay. It goes red on today's main, which proves it can fail.
- CLI: the status label for `PipelineStatus.Active` reads `følger med`, and
  `track <orgnr> active` still parses.

**Wave 2**
- C# `CountOpenByEmployerAsync`: an open ad counts. Expired, inactive and hidden ads do not.
  A branch's ad counts for the branch, not the parent. A company with no ads is absent and
  maps to 0.
- C# `/api/companies` and `/api/new` return `openAds`. `/api/status` returns `version`, and
  `dev` in tests.
- Web filter: «Med åpen annonse» hides companies with 0. A group whose only open ad belongs
  to a branch still shows, with the group total as its count. The filter combines with
  search.
- Web footer: the version shows when status has it and is absent when the fetch fails. The
  links have the right `href` and `rel`.
- Web logo: a link to `/` with the accessible name from B1.
- Web «Nytt siden sist»: company links point at `/companies/{orgnr}`, place headings carry
  counts and the screen-reader suffix (the visible count is `aria-hidden`; singular and
  plural both covered), and ads group under `kommuneNavn` (or «Ukjent sted»).
- Web detail close: opened from the dashboard, close lands back on the dashboard with focus
  on the opening link. Opened from a cold `/companies/{orgnr}` load, close lands on
  `/companies`.
- Web company list: the result line has `role="status"` and its text follows the new filter.

**Live check after each wave** in the browser pane, against a scratch config:
- Measure the description's offset under each heading. Measure `.text-muted` contrast
  against the card background in both themes (4.5:1 minimum for body-size text).
- Check the footer and filter row at 320 px, 375 px and 1280 px, with and without the demo
  banner. Every control on the filter row is 44 px tall with one bottom edge. Every footer
  link's hit box is at least 44 px tall.
- Keyboard walk: Tab to the logo, then Enter (dashboard heading focused). Open a company from
  «Nytt siden sist», then close it (focus back on that link).
- Toggle EN and NB on every changed string.

## Out of scope, and known seams

- **Company detail as a dialog** is the reviewer's work. B5 only needs `/companies/{orgnr}`
  to stay a working link.
- **TanStack Query migration** is also the reviewer's. Wave 1 does not touch data fetching.
- **shadcn/ui**: not in Hugin (it needs Tailwind and clashes with the workbench design
  system). Any ideas from it go to a workbench brainstorm.
- **The export's «Aktiv» section** keeps its name (decision 3). Renaming it would change a
  file format that scripts read.
- `openAds` counts ads by the employer orgnr only. An ad manually linked to a sister company
  (`LinkedOrgnr`) counts for its employer, not the linked company. The link exists for the
  pipeline, not the register view.
- The version reads `dev` under `dotnet run` and in tests. Only published builds carry a tag.

## Stress-test record (2026-10-02)

Five lenses: security, privacy, accessibility, legal, loopholes. Every finding is folded into
the sections above.

**Applied**
1. 🟠 Loophole: the detail's close button always went to `/companies`, so a company opened
   from the dashboard closed into the wrong view. B5 now requires close to return to the
   origin with focus on the opening link, and C tests it.
2. 🟡 Accessibility: small footer text would have given small link targets. B2 sets a 44 px
   hit box per link.
3. 🟡 Accessibility: the place count would have been read twice («· 3» plus the suffix). The
   visible count is now `aria-hidden`, with singular and plural spelled out for both
   companies and ads.
4. 🟡 Accessibility: the logo link's focus and scroll behaviour was unstated. B1 now says it
   is the same navigation as «Oversikt».
5. 🟡 Legal: «Data fra NAV og Brønnøysundregistrene (NLOD)» implied NAV's data is NLOD. The
   credit now splits the two, with sources read on 2026-10-02.
6. 🟡 Loophole: footer reflow was only checked at 375 px. 320 px is added.
7. 🟡 Loophole: the guard test for «Aktiv» was too broad to pass («aktive annonser» stays).
   It now names three keys and must fail on today's main.
8. 🟡 Accessibility: `.text-muted` contrast in both themes is now measured, not assumed.

**Adapted**
1. 🟡 Loophole: reading the version from the entry assembly returns the test host's version
   under `WebApplicationFactory`. Read from `typeof(Program).Assembly` instead. That beats
   special-casing tests, because the same line is right in production and in tests.
2. 🟡 Loophole: the version is read before `npm run build`. `wwwroot/` is gitignored, so the
   build cannot make the tree `-dirty` today. Reading first costs nothing and keeps it true
   if that ever changes.
3. 🟡 Accessibility: a filter change was silent for screen readers. The obvious fix was a new
   live region for the new filter. Putting `role="status"` on the existing result line fixes
   all three filters with one attribute.

**Security and privacy: clean.** No new write paths. `openAds` counts open ads only, which is
what public mode already shows. The version and kommune names render as React text, never as
HTML. External links keep `noopener noreferrer`, and the server already sends
`Referrer-Policy: no-referrer`.

**Considered and rejected**
- **The version string discloses the build.** The repo and releases are public, so the
  footer tells a visitor nothing they cannot already read.
- **A `CONTRIBUTING.md` inbound licence line before the reviewer's PRs.** The repo has an
  MIT `LICENSE`, and GitHub's terms of service (section D.6) license contributions under the
  repo's licence by default. Nice to have, not a blocker.
- **Counting ads linked by hand (`LinkedOrgnr`) in `openAds`.** The link serves the
  pipeline. Counting it in the register view would make one ad show under two companies.
- **Renaming the export's «Aktiv» section.** Decision 3: it is a file format that scripts
  read, and it already means open ads.
